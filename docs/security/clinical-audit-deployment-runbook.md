# Clinical Audit Integrity Deployment & Rollback Runbook

This runbook covers production deployment and rollback procedures for the clinical audit
integrity path: `MedicalConclusion`, `MedicalResult`, `BlockchainLogger`, `AuditBatch`,
Merkle anchoring, and `AuditAnchor.sol`.

## Scope

The audit system anchors only cryptographic integrity data on-chain.

Never store the following on-chain:

- patient identifiers or demographics
- clinical notes, diagnoses, treatment plans, prescriptions
- medical files, PDFs, X-Rays, Cloudinary URLs, or file names
- raw AI output or biometric data

On-chain data is limited to:

- batch ID
- Merkle root
- leaf count
- block timestamp / transaction metadata

## Pre-deployment Checklist

### 1. Code and test gate

Run backend tests:

```bash
npm test -- --runInBand --runTestsByPath \
  src/infrastructure/audit/merkle.util.spec.ts \
  src/infrastructure/audit/audit-hash.util.spec.ts
```

Run backend build:

```bash
npm run build
```

Run AuditAnchor contract tests:

```bash
npm test -- --grep AuditAnchor
```

Expected result:

- backend audit tests pass
- backend build succeeds
- Hardhat `AuditAnchor` tests pass

### 2. Environment gate

Production must set:

```env
NODE_ENV=production
AUDIT_PEPPER=<64 hex chars generated by a secure secret manager>
BLOCKCHAIN_RPC_URL=<production RPC URL>
AUDIT_ANCHOR_ADDRESS=<deployed AuditAnchor address>
```

`AUDIT_PEPPER` requirements:

- must not be stored in the database
- must not be committed to Git
- must be backed up in the production secret manager
- changing it breaks recomputation of new hashes unless handled as a formal key rotation event

### 3. Contract deployment gate

Deploy exactly:

```text
blockchain/contracts/AuditAnchor.sol
```

Do not change these domain constants after deployment:

```solidity
KLTN_AUDIT_LEAF_V2
KLTN_AUDIT_NODE_V2
```

The backend uses the same canonical byte semantics through `MERKLE_SHA256_BYTES32_V2`.

### 4. Database migration gate

Apply Prisma migrations before enabling production traffic:

- `20260610183800_audit_batch_algorithm_version`
- `20260610193000_harden_blockchain_logger_immutability`
- `20260610193100_harden_audit_batch`

These migrations enforce:

- append-only audit log content
- one-way anchoring metadata
- immutable audit batch checkpoint fields
- no overlapping anchored batch ranges

## Deployment Order

1. Stop or drain clinical write traffic.
2. Back up the database.
3. Deploy `AuditAnchor.sol` and record its address.
4. Apply database migrations.
5. Set production env secrets and contract address.
6. Deploy backend.
7. Start backend in production mode.
8. Run a controlled smoke test:
   - create a non-real clinical audit event in staging/controlled environment
   - ensure `BlockchainLogger` row is created
   - trigger anchoring
   - verify `AuditBatch` transitions to `ANCHORED`
   - verify `AuditAnchor.getRoot(batchId)` returns the expected root
9. Re-enable traffic.

## Rollback Strategy

### Application rollback

If backend deployment fails before clinical traffic resumes:

1. Roll back backend image/code.
2. Keep DB migrations in place if already applied.
3. Do not manually edit `BlockchainLogger` or `AuditBatch` rows.

Reason: the DB hardening migrations are protective and should not be removed casually.

### Contract address rollback

If the deployed contract address is wrong or points to the wrong network:

1. Stop audit anchoring jobs immediately.
2. Correct `AUDIT_ANCHOR_ADDRESS` and `BLOCKCHAIN_RPC_URL`.
3. Restart backend.
4. Run `recoverPendingBatches()` path through normal service startup.
5. Confirm pending batches are recovered only when exact local Merkle membership matches on-chain state.

### Failed batch handling

If a batch is marked `FAILED`:

1. Do not mutate the failed row manually.
2. Investigate RPC/contract/operator error.
3. Let the next anchoring cycle create a new valid batch from unanchored logs.
4. Preserve the failed row as part of the operational audit trail.

### Suspected tampering

If append-only triggers reject writes or recovery validation fails:

1. Treat as an integrity incident.
2. Freeze clinical audit writes if necessary.
3. Export affected `BlockchainLogger` and `AuditBatch` rows.
4. Compare:
   - local `entryHash`
   - local recomputed Merkle root
   - on-chain root
   - transaction hash and block number
5. Do not repair by direct SQL unless a formal incident record and legal/compliance approval exist.

## Post-deployment Verification

After deployment, verify:

- `NODE_ENV=production`
- `AUDIT_PEPPER` exists and is non-empty
- backend starts without audit pepper errors
- `AUDIT_ANCHOR_ADDRESS` points to the deployed `AuditAnchor.sol`
- new `AuditBatch` rows use:
  - `algorithmVersion = MERKLE_SHA256_BYTES32_V2`
  - `contractVersion = AUDIT_ANCHOR`
- anchored `BlockchainLogger` rows have one-way metadata populated:
  - `batchId`
  - `txHash`
  - `blockNumber`
  - `anchoredAt`

## Operator Warnings

- Never run `prisma db push` in production as a substitute for migrations.
- Never manually update audit hashes, entry hashes, batch IDs, tx hashes, or block numbers.
- Never re-anchor old batches under a changed Merkle algorithm.
- Never store medical/PII payloads on-chain.
